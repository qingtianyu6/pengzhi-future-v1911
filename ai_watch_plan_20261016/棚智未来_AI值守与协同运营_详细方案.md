# 棚智未来「AI值守与协同运营」详细建设方案

版本：方案 V1.0  
日期：2026年10月16日  
范围：基于当前项目的产品与开发方案。本文中的新增功能、参数与验收指标均为拟建设内容，不表示已经上线或已通过现场验证。

## 1. 产品定位与首期目标

产品定位：AI持续关注大棚环境、数据链路与农事任务，在授权范围内主动推进处理，并把需要人员判断的事项交给相应人员确认。

首期围绕四项能力：

1. 环境异常发现与处理跟踪。
2. 设备断线、数据异常检查。
3. 农事任务提醒与复查。
4. 每日生产情况汇总。

首期“托管”的含义是持续观察、创建事件、组织证据、形成建议、安排或建议任务、跟踪复查、汇总结果。现场巡棚、拍照、实际执行仍有人员参与。

真实设备自动控制为第二阶段：需要设备协议、硬件互锁、执行回执、手动接管和现场验收。首期可以通过模拟适配器演示该接口，但必须标注模拟，不宣称已经控制硬件。

对外介绍建议：
“棚智未来以AI持续值守大棚环境与生产任务，主动发现异常、组织处置、跟踪复查，并保留每一步的依据和人工决策记录。”

## 2. 当前基础与新增范围

以下根据当前代码核对，不代表本次完成了所有功能的运行验收。

| 环节 | 已有基础 | 本轮需要建设 |
| --- | --- | --- |
| 环境与风险 | 环境记录、趋势、预测、预警、风险解释 | 按组织与大棚启用的后台自动扫描、连续异常判定、事件合并与恢复判定 |
| 农事任务 | 草稿、提交、分配、执行、反馈、完成、取消 | 值守事件与任务唯一关联、提醒策略、重复任务检查、逾期升级 |
| 智能体 | 查询工具、运行记录、操作审批、步骤日志 | 从事件主动创建运行、服务身份和委托授权、运行预算与可恢复事件队列 |
| 后续复查 | AgentRecheck持久化、到期读取数据、恢复运行 | 区分数据不足与未达标、复查状态在值守中心可见、异常升级 |
| 案例与证据 | 案例记忆、处置案例、任务证据链 | 自动形成待复核的运营记录、统一关联事件与日报 |
| AI交互 | 棚小智、对话、待确认操作、处理状态 | 主动事项卡片、值守状态入口、全局接管与停止 |
| 权限 | 组织、大棚、角色及操作检查 | 细到动作的委托范围、授权有效期、审批失效校验 |
| 知识 | 10条结构化本地知识与检索接口 | 审核发布、适用条件筛选、引用可追溯、游客独立接入 |
| 每日报告 | Agent可汇总已读取证据 | 定时统计、固定统计口径、报告版本、定时发布和阅读反馈 |
| 设备执行 | 三维交互与处置模拟 | 真实设备接入、命令状态、回执、互锁与现场验证，安排在第二阶段 |

现有Agent运行、审批、工具调用、复查表可以复用。当前定时复查工作器在后端运行，已有原子领取部分复查任务的逻辑；新增值守调度仍需验证多实例领取、崩溃恢复与重复写入，不能据此直接认定具备生产级可靠性。

## 3. 值守模式与授权设计

平台提供三种首期模式：

| 模式 | 可自动完成 | 需要人员确认 |
| --- | --- | --- |
| 观察模式 | 读取数据、识别事件、汇总信息、展示提醒 | 业务记录变更、创建现场任务 |
| 协同模式，建议默认 | 观察、分析、整理证据、形成待确认操作 | 创建或变更农事任务、安排影响生产的事项 |
| 授权任务模式 | 在单独授权范围内创建巡查任务、发送站内提醒、安排复查、生成报告 | 超出授权范围、存在冲突、关键条件缺失的操作 |

第二阶段另外开放“受控设备操作”。这不是前三种模式的默认附带权限。

授权字段至少包括：组织、大棚、场景、可调用动作、参数上限、责任人、起止时间、通知方式、是否允许安排复查、撤销状态。

例：允许“番茄A棚高湿事件→创建巡棚任务”，不代表允许分配任何人员、不代表允许开窗，也不代表允许关闭任务。分配任务只能使用授权名单；任务完成继续满足现有执行状态、反馈与复查条件。

服务在动作执行和审批恢复时再次检查权限。账号停用、角色变更、委托过期或大棚归属改变后，未执行动作暂停并转交人员处理。

## 4. 用户页面与交互方案

### 4.1 新增“AI值守中心”

导航建议放在“生产总览”之后，原有六个业务入口保留。

顶部展示：

- 值守范围：当前大棚/所选大棚，不跨组织。
- 值守模式：观察、协同、授权任务。
- 后台心跳：最近检查时间、下一次预计检查。
- 数据状态：正常采集、历史数据、数据不足、采集异常。
- 操作：配置值守、暂停值守、查看记录。

“已开启”只表示配置启用；只有后台心跳、数据时效和扫描正常时才显示“正在值守”。断线时不能继续显示绿色“运行正常”。

中部四张工作卡：

1. 环境值守：待处理环境事件、正在跟踪的处理、下一次复查。
2. 数据与设备：延迟/断线设备、异常指标、最近恢复。
3. 农事跟进：待确认、临期、逾期、待复查。
4. 生产日报：最近报告、统计时间范围、待阅读与待确认事项。

下部为事项列表，可按大棚、场景、严重程度、负责人和处理状态筛选。

### 4.2 事项详情

固定展示六个部分：

1. 发生了什么：指标、数值、单位、时间、关联设备。
2. 为什么触发：规则、持续时间、适用作物与阶段、数据质量。
3. AI读取了什么：数据快照、知识版本、相关任务与案例。
4. 下一步做什么：允许动作、执行条件、待确认事项。
5. 实际推进到哪一步：审批、任务、回执、复查、失败原因。
6. 当前结果：已改善、仍异常、数据不足、人工接管或已关闭。

每个状态使用文字、图标与颜色共同表达。指令已发出、设备已执行、环境已改善分别显示。

### 4.3 与现有页面联动

- 总览：展示“AI正在跟踪X项事项”，进入值守中心。
- 预警：增加对应值守事项、处理负责人和复查进度。
- 农事：显示“来自AI值守”的来源，链接原始事件。
- 三维：点击异常区域可查看同一事件；模拟与真实状态分开标识。
- 棚小智：展示主动事项卡片，支持解释、确认、停止本轮处理。
- 侧栏：聚合待确认与待复查，避免重复展示首页整段建议。

棚小智保留当前独立悬浮、完整3D形象和原有动作，不因本方案自动缩成小图标或改成侧栏人物。

### 4.4 提醒方式

首期使用站内提醒和页面待办。浏览器通知需用户主动授权；短信、邮件、企业通信工具为后续可配置渠道，本方案不默认接入或发送外部消息。

## 5. 数据和事件处理方法

后台按配置周期检查，前端只负责展示和交互。网页关闭后，后台仍应继续值守；后端关机或服务停止时无法继续监控，需由部署环境提供持续运行和故障告警。

单次处理：

1. 接收新采样或到期扫描。
2. 校验大棚归属、设备绑定、时间、单位、质量标记与字段范围。
3. 按作物、生育阶段和启用规则判断持续异常。
4. 写入或更新事件，保存触发证据。
5. 领取待处理事件，启动或恢复已有Agent运行。
6. 输出结构化计划，校验权限与动作范围。
7. 执行软件动作或等待确认。
8. 保存结果，安排复查、通知或关闭。

环境阈值由农技人员配置和审核，不由模型临时猜测。资料没有给出适用条件时，保留“待确认”，不自动发布为可执行规则。

事件主状态建议：
待分析、处理中、等待确认、等待现场执行、等待复查、已恢复、已转人工、已停止、处理失败。

这些是运营事项状态，与Agent运行状态、农事任务状态分别维护。AI本轮运行完成，不等于现场任务完成；环境恢复，也不等于某项操作导致了恢复。

## 6. 能力一：环境异常发现与处理跟踪

### 6.1 识别范围

首期支持空气温度、空气湿度和土壤湿度；CO₂与光照可先观察和提醒，再按设备数据质量扩展。

每条规则需保存：指标、单位、作物/阶段、大棚、触发方向、触发阈值、持续时间、最少有效采样数、恢复阈值、恢复持续时间、冷却时间、优先级、负责人和允许动作。

“生长异常”需更多现场证据；单个环境指标越界首先记录为环境异常或待核实风险。

### 6.2 高湿场景

触发：有效数据连续达到配置条件，且没有同一规则的活动事件。

处理：

1. 保存触发窗口与数据质量。
2. 查询当前批次、活动预警、天气可用性、已有任务与知识依据。
3. 先检查是否有正在执行的通风或复测任务，避免重复安排。
4. 给出疑似原因与现场检查步骤，不把相关性写成确定病因。
5. 协同模式生成待确认任务；授权模式按许可创建限定类型的巡查任务。
6. 人员执行并记录反馈。
7. 到期读取新数据；需要同时满足数据新鲜、质量有效、目标范围和持续恢复要求。
8. 已恢复则记录恢复证据；仍异常则有限重评；无数据则转数据异常处理，不能判定成功。
9. 超过复评次数、条件冲突或风险升级，转交人员。

首期设备动作以“建议现场处理”或明确标注的模拟接口呈现。

### 6.3 防止重复和频繁触发

同一组织、大棚、规则及事件实例只允许一个活动处置。采用持续窗口、触发与恢复不同边界、冷却期和任务去重。

同一事件可能被扫描多次或消息重复投递，但不能因此重复创建任务、重复通知或重复操作设备。

## 7. 能力二：设备断线与数据异常检查

### 7.1 要区分的问题

| 类型 | 判定依据 | 首期处理 |
| --- | --- | --- |
| 数据上报延迟 | 超过该设备配置的正常上报间隔和容忍时间 | 标记延迟，检查接入链路，提醒负责人 |
| 设备疑似断线 | 有心跳定义时心跳超时；无心跳时只称“数据中断” | 生成检查事项，按授权重试连接或读取状态 |
| 可疑读数 | 单位不符、物理范围不合理、突变、异常时间戳 | 标记可疑，保留原始值，建议复测或校准 |
| 长时间不变化 | 足够长的连续窗口中数值固定 | 标记待核实；不能直接判为损坏 |
| 后端采集故障 | 接入失败率、工作器心跳或队列异常 | 平台维护提醒，避免批量误报所有设备故障 |

离线时间不能一刀切：按照每个设备的预期上报间隔设置。例如工程测试可使用“超过3个上报周期并且至少5分钟”的条件；这是测试配置示例，不是所有设备的固定标准。

### 7.2 故障处理边界

AI可查询状态、执行预先批准且有限次数的连接重试、整理检修步骤、创建任务。

首期不自动远程刷固件、修改校准参数、删除历史记录或重启生产设备。网关重启等能力只有在第二阶段明确授权并确认对现场影响后才开放。

恢复时检查连续有效数据，保留异常期间的数据缺口。异常数据不直接覆盖原始记录，也不直接进入可执行环境策略。

## 8. 能力三：农事任务提醒与复查

### 8.1 自动关注的事项

- 任务即将到期但未开始。
- 任务已经逾期。
- 执行中长时间无反馈。
- 有处理任务但未安排复查。
- 到期复查没有有效新数据。
- 同一风险存在重复或相互冲突的安排。

提醒时间、宽限期、升级间隔和接收人可配置。每条提醒具有唯一去重键和发送状态，避免每次扫描重复提醒。

### 8.2 提醒和升级

首次提醒负责人；超过配置宽限期仍无进展，进入管理人员待办；负责人停用或未分配时直接进入“待分配”事项。

AI可以提出负责人或时间调整建议。更改负责人、优先级或计划时间需满足相应授权，保留原值、变更原因及操作人。

### 8.3 复查与完成

复用当前AgentRecheck机制。复查必须读取约定时间之后的新数据，检查质量、时效、目标范围；持续改善场景还应读取时间窗口。

结论分为：达标、未达标、证据不足。人员观察与数据结论分别保存，存在冲突时提交人工复核。

完成任务继续经过已有任务服务和权限校验。不能仅凭“湿度恢复”自动声称现场人员执行了通风。

现有复查数量存在上限，新增值守同样设置全局和单事件上限，避免多个运行相互接力导致无限复查。

## 9. 能力四：每日生产情况汇总

### 9.1 时间与口径

建议默认每天07:30（Asia/Shanghai）生成前一日完整日报，并附生成时刻的当前待办。时间可配置。

日报统计区间：前一天00:00至当天00:00，左闭右开。当前待办是独立快照，不混入前一日统计。

### 9.2 固定内容

1. 大棚与批次概况。
2. 各指标的有效样本数、覆盖情况、可用的最大/最小/均值与异常持续时间。
3. 新增、持续、恢复和转人工的风险事项。
4. 新增、完成、逾期与待复查任务。
5. 设备延迟、数据中断、恢复情况及缺失时间段。
6. AI调用、审批、失败和人工接管记录。
7. 当前待办与需要负责人决定的事项。
8. 数据来源、统计范围、生成时间与报告版本。

统计由后端计算，AI只负责解释和组织语言。无数据时显示“无可用记录”，不能写成0次风险或正常。

风险次数按事件口径统计，持续越界的多条采样不是多次独立风险。预测、模拟、实测和人员反馈分别标明。

### 9.3 版本与发布

同一组织、大棚、日期和报告类型建立唯一记录。后续补录或纠错生成新版本，注明变更；不覆盖旧报告，不重复发送相同通知。

模型不可用时仍可生成统计版日报，AI解读标记暂不可用。对话模型故障不能阻断基本统计和待办提示。

## 10. 技术落地与数据结构

### 10.1 总体组成

保持当前React/TypeScript前端与Python/FastAPI后端，复用现有业务服务和Agent运行框架。

新增能力按职责组织：

- 值守策略：范围、规则、负责人、模式与授权。
- 事件扫描：环境、设备/数据、农事、日报到期。
- 运行分发：将事件转换成有身份、有预算的Agent运行。
- 通知与报告：站内提醒、日报统计与版本。
- 设备适配：第二阶段才接入真实执行。
- 恢复与审计：心跳、领取、超时、补偿、日志与人工处理。

首期可以在现有后端内划分模块。部署时即使只有一个工作器，也必须通过数据库条件更新与唯一约束保证重复触发不会重复写业务记录。扩大部署后再把扫描和执行拆成独立工作器；不依赖浏览器计时器。

### 10.2 建议新增的数据对象

以下名称是开发建议，不是现有接口承诺。

| 对象 | 主要字段 |
| --- | --- |
| WatchPolicy | organization_id、greenhouse_id、scene、mode、enabled、rule_version、owner、授权与有效期 |
| WatchIncident | 类型、严重程度、规则版本、关联预警、首次/最近发生时间、恢复时间、证据快照、状态 |
| WatchRunLink | incident_id、agent_run_id、责任身份、触发原因 |
| ActionExecution | action_id、幂等键、目标、参数、授权快照、执行状态、回执与失败原因 |
| Notification | 事项、接收人、渠道、唯一键、发送状态、升级次数 |
| DailyReport | 组织/大棚、日期、时区、统计区间、统计结果、解释、证据引用、版本 |
| WorkerHeartbeat | 工作器标识、最近心跳、最近成功扫描、积压与失败数 |
| DeviceProfile | 绑定大棚、数据通道、上报间隔、心跳能力、可查询/可执行能力 |

复用AgentRun、AgentStep、AgentToolCall、AgentApproval、AgentRecheck以及现有任务、预警、案例表。新增关联和索引，而不是另做一套任务生命周期。

### 10.3 建议接口

- 查询与配置当前组织的值守策略。
- 启用、暂停或撤销指定大棚的值守。
- 查询事项列表、详情与事件时间线。
- 人工接管、重试允许的失败步骤、停止指定运行。
- 查询/审批待确认动作，复用现有Agent审批链。
- 查询日报、按日期重新生成版本。
- 查询值守后台心跳与积压。

所有接口重复执行身份、组织、大棚及动作权限校验。服务账号通过显式授权成为执行主体，不通过把后台任务伪装成管理员请求获取权限。

## 11. AI与确定性规则的分工

| 工作 | 承担方式 |
| --- | --- |
| 单位、时间、质量校验 | 后端确定性规则 |
| 持续越界、数据中断、任务逾期 | 可配置规则和调度 |
| 统计、状态变更、权限与去重 | 业务服务和数据库约束 |
| 解释问题、检索知识、提出排查顺序 | AI基于证据完成 |
| 判断工具调用是否合法 | 独立权限与参数校验 |
| 执行生产设备动作 | 第二阶段的受控设备适配器 |
| 判断复查是否满足数据目标 | 后端规则，AI解释结果 |
| 形成通用农业经验 | 人员审核后发布 |

AI输出采用结构化动作：动作类型、目标大棚、关联事件、依据、前置条件、参数、是否需要确认、复查目标和停止条件。字段校验失败则不执行。

知识库、网页、设备备注和用户反馈均按资料处理，其中的文本不能改写系统权限或触发未授权操作。业务动作使用预先登记的工具，不执行模型临时生成的任意脚本。

## 12. 可靠性、运行预算与设备边界

1. 数据处理使用采样时间和接收时间，识别乱序、重复、未来时间和延迟补传；按设备、时间和记录标识去重。
2. 事件、任务、提醒、日报分别设置唯一约束。消息按可能重复到达设计，不假设天然只执行一次。
3. 后台任务具有原子领取、租约、超时与重启恢复策略。租约到期前确认旧执行状态，避免两个工作器同时推进同一动作。
4. 模型调用设置超时、每运行步骤上限、每事件重规划次数与组织每日预算。达到上限转交人员；基础扫描、通知和统计继续运行。
5. 人工审批绑定具体动作、参数、事件证据和有效期；数据或方案发生关键变化后重新审批。拒绝一次操作不被另一运行重新提交同一动作绕开。
6. 每次执行前重新核对委托和资源归属。停止值守后不再派发新动作，待审批动作失效；已开始的动作按状态处理，并告知人员哪些记录已写入。
7. 首期停止运行不删除已经创建的任务，也不自动把任务标记完成。
8. 第二阶段设备命令具有命令ID、参数上限、设备互锁、回执和超时状态。回执丢失时标记“执行状态未知”，先查询设备再决定是否重试，不能盲目重复开关。
9. 设备失联时不能保证云端停止指令到达。因此必要的断网策略、最长运行限制和紧急停止须在设备/网关侧落地并现场验证。
10. 通风、遮阳、灌溉等动作可能互相影响，必须有冲突检测和独占/互锁规则。药剂与施肥等事项不在首期自动设备执行范围。
11. 数据和事件有备份与恢复演练；日志记录规则版本、知识引用、模型/工具版本、决策人、执行与复查证据。
12. 自动化覆盖率、采样在线率、模型可用率分别统计，不把其中一个健康状态当成整个系统健康。

## 13. 工程配置与验收口径

以下数值仅作为工程测试起点，不是农艺阈值，也不是当前系统已达到的性能承诺：

- 后台扫描可先配置为30秒；设备原始上报周期单独登记。
- 连续异常与恢复持续时间由规则配置；测试可使用压缩时间，正式运行不能沿用压缩时钟。
- 同一事件有限重评，建议初次分析后最多2次自动重评；复查次数同时受现有机制及事件预算限制。
- 第一轮模型调用失败只做有限重试，之后生成“需要人员检查”事项。
- 日报默认07:30，统计前一天；通知频率、工作时段和升级间隔可配置。

至少验证下列场景：

| 场景 | 必须看到的结果 |
| --- | --- |
| 正常连续数据 | 无误触发，后台心跳与检查时间更新 |
| 单次瞬时越界 | 按规则记录，不错误启动持续异常处置 |
| 持续有效越界 | 形成一条活动事件，证据窗口完整 |
| 重复采样/重复扫描/重复消息 | 同一动作不重复创建任务或发送提醒 |
| 旧数据和未来时间戳 | 不作为当前异常或成功复查的依据 |
| 数据缺失或设备中断 | 转数据异常，禁止自动宣称环境恢复 |
| 模型超时、不可用、预算用尽 | 基础值守继续，AI分析标明未完成并转交 |
| 未授权或跨组织操作 | 请求被拒绝，留有审计记录 |
| 审批后参数变化/授权被撤销 | 执行前再次拦截或重新审批 |
| 服务重启 | 待审批、待复查保留；未完成动作不盲目重放 |
| 两个工作器同时领取 | 最终只产生一次对应业务副作用 |
| 人员拒绝或暂停 | 不继续执行被拒绝或新派发的动作 |
| 复查数据达标但现场任务未开始 | 不自动认定现场任务已完成 |
| 任务逾期且无人接单 | 进入负责人/管理员待办并有限升级 |
| 一天完全没有数据 | 日报明确缺失，不能描述为生产正常 |
| 同一日报重复生成/补录 | 产生可追溯版本，统计不重复、通知不刷屏 |
| 第二阶段设备无回执 | 标记未知/失败，禁止宣称执行成功 |
| 设备断网与紧急停止 | 按现场验证的本地策略退出并通知人员 |

检测时延建议验收口径：在声明的测试负载下，满足触发条件且有效数据已入库后，不晚于两个扫描周期形成事件；模型响应和现场处理时间单独统计。初始测试负载可设10座大棚、100个数据通道，实际指标以测试报告为准。

业务收益评估记录：发现到通知时长、确认到开始执行时长、逾期率、完成反馈率、复查证据完整率、人工误报确认率、AI分析成本。未做对照或现场试用前不宣称节省百分之多少人工或降低多少病害。

## 14. 实施里程碑

| 阶段 | 建设内容 | 完成条件 |
| --- | --- | --- |
| M0：规则与样例 | 确定一座演示番茄棚、指标、规则、角色与测试数据；明确正式和演示边界 | 规则表、授权表、场景脚本、验收问题通过内部评审 |
| M1：事件与后台 | 新增策略、扫描、事件去重、后台心跳、重启恢复；先观察模式 | 环境、数据、任务、日报到期四类触发可见；关闭网页不影响后台 |
| M2：环境协同 | 事件进入现有Agent、知识引用、审批、任务与复查 | 高湿“发现—确认—任务—反馈—复查”完整跑通，无重复任务 |
| M3：设备数据与农事 | 延迟/中断识别、数据排查、临期逾期提醒、升级 | 能区分采集故障与环境异常，有限提醒，权限正确 |
| M4：日报与界面 | 固定统计、报告版本、值守中心、棚小智主动事项卡 | 四项首期能力在统一页面可见，证据可追溯 |
| M5：上线验收 | 异常、重启、并发、权限、成本和回退演练 | 验收记录、部署说明、责任人与接管流程齐全 |
| M6：真实设备联调 | 设备协议、命令、回执、本地保护、互锁与现场试用 | 完成特定设备、特定动作的独立现场验收后开放对应权限 |

本方案不设未经评估的完工日期。开发排期需要结合人员、硬件型号、数据可用性和现场条件确定；首期软件闭环不等待所有硬件自动控制完成。

## 15. 答辩演示安排

5—8分钟内展示一个完整案例，而不是逐页介绍所有功能。

1. 约40秒：总览展示值守范围、正常采样和后台状态。
2. 约60秒：演示回放持续高湿，解释为何触发一条事件。
3. 约60秒：棚小智展示本棚证据、知识来源与建议，人员确认巡查任务。
4. 约60秒：执行人员开始任务、填写现场反馈。
5. 约60秒：演示到期复查，展示有效新数据和恢复/转人工结果。
6. 约40秒：切换到数据中断事件，展示系统区分环境与采集问题。
7. 约40秒：打开日报，回看事件、任务、反馈和当前待办。

时间压缩、历史回放、模拟数据或模拟设备回执必须醒目标注。若没有实物联动，展示软件任务闭环即可，不把三维开关当成硬件执行证据。
